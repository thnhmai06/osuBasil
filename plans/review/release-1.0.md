# Release 1.0: goals, open findings and roadmap

## Why this page exists

Basil moves from `v1.0.0-alpha.1` to `v1.0.0`. This page is the one working record of that work: what the owner
decided, the release criteria, every finding that is still true, the open questions and the roadmap. It is working
material and is not part of `docs/`. The evaluation of 2026-11-17 and 2026-11-18 (86 findings, three reports, a
handoff note) was checked against the code of 2026-11-24 and merged here; a closed finding is deleted, and git keeps
its history. Paths are relative to the repository root; the projects live there since the flattening.

## Decisions of the owner

## Release criteria

`v1.0.0` is tagged only when every line holds, checked on the released Docker image (P2) with real clients, and every
blocker below is closed. Each line is a check that passes or fails. Lines that are already met were dropped.

**Every surface**

* Every answer a client reads says that the server answered, what really happened and what to do next. Every
  client-facing text lives in its surface's reply class and went through the humanizer (D12). A refusal names its
  reason and next step; `Denied` names the role that can act (D4). One situation has one wording on every surface.
* One number names a room on every surface, and a match has its own stable number (F-019).

**osu! (stable) client**

* Every flow behaves as bancho.py does with the same client (D11): sign-in, presence and stats, chat (public, private,
  `#multiplayer`, `#spectator`), lobby, room create/join/leave, slot moves and locks, ready, host transfer, beatmap and
  mods, start, loading, skip, live scores of every player on the scoreboard, fail, completion, results, spectating
  with live score.
* A player's own action reaches their own client in the answer to the request that carried it (F-056, batch 2), and a message
  from another user arrives within one poll interval of the receiver.
* A real client plays a full multiplayer round (two clients, one round, results shown) with no client exception in
  `runtime.log`; a round whose players cannot load ends by itself; a room never stays without a host.
* A normal client is never refused by the rate limit during a session of play (F-045, batch 2).

**IRC and BasilBot**

* Irssi, WeeChat and Halloy connect, join, chat and run every BasilBot command with no error line from the server's
  answers to their own housekeeping commands (F-018).
* Every BasilBot command answers, and every privacy rule holds for a user with no role (F-006).

**HTTP API and SSE**

* The OpenAPI document describes every route's body, answers and errors (F-022, F-067); a Postman collection ships
  and runs green against a fresh server.
* Every refusal follows the envelope contract; privileges and enums are named values in and out (F-025, F-082).
* The spectate stream has separate `replay` and `activity` events, allows spectating oneself and a player who is not
  playing, and stops only when the player goes offline (F-040 to F-042).

**Operation: console, dashboard, Docker**

* `docker compose up` on a clean machine with only Docker gives a working server following the docs alone; `shutdown`
  stops it and `restart` restarts it (F-069).
* Every documented key, dialog and mode of the dashboard works as `console.md` says (F-049, F-050, F-071 to F-074);
  no enum number is shown or required (F-053); settings show effective values with units (F-046, F-047).
* The shipped logging writes lifecycle lines only, with a log per session (F-036, F-037).

**Performance (D5, D6)**

* The load test reports the ceiling (users, requests per second) with memory and CPU at each step, on PostgreSQL after
  P1; chat and room actions stay within the latencies of F-039 (batch 2) at the target load.

**Documentation**

* Every statement in `docs/` matches the code; a newcomer of each audience can do the first task from the docs alone;
  the client starter material ships (D10).

**Code**

* Build with no warning except the documented, assessed suppressions; no known high-severity advisory unassessed
  (F-068); no finding of F-080 to F-085 left.

## Open findings

Severity is the owner's grading of 2026-11-17 and 2026-11-18: F-005 to F-016, F-021 to F-031, F-061 to F-077 and F-078
to F-085 are all blockers; "not graded" means the owner has not graded it yet (proposed: blocker).

### osu! (stable) client

**F-044 and F-033. The client's slot numbers are used unchanged against 1-based slots.** Blocker, correctness. Basil
numbers slots from 1 (`Basil.Domain/Multiplayer/Room/RoomSlots.cs`, the indexer takes `1` to `16`). The host passes
the client's number straight to the operations: `MatchChangeSlot`, `MatchLock` and `MatchTransferHost` in
`Basil.Host.Stable/Packets/PacketHandlers.Multiplayer.cs`, and `ForwardScore` stamps each live score with
`Id = slot.Index`. Confirmed with the real client on 2026-11-18: clicking the fifth row put the player in slot 4,
clicking the second row put them in slot 1, clicking the first did nothing. The score frame carries the same shift, so
every live score is drawn against the next slot (an empty one, or another player) and the player in slot 16 sends an id
past the end; this matches the owner's report that the scoreboard shows nobody during a round (F-033). Fix: convert at
the host boundary (`WireMap`), in both directions, and compare with bancho.py's 0-based slot ids.

**F-058 and F-054. The client throws when a round starts, and the host never gets a Start button.** Not graded,
cause unknown. On 2026-11-18, with a beatmap whose hash equals the client's file, starting a round through the API made
the client throw a `NullReferenceException` 0.2 s after the start packet, post `osu-error.php` and show "installing the
beatmap failed". Earlier the same client showed no Start button to the host of a room. The server side looked right
against the layout of `main`; candidates are a field of the start packet or of another packet in the same answer, and
the slot shift of F-044. To do: capture the bytes of that poll answer (a scripted second player in the room), decode
them against bancho.py's layout, and retry after F-044 is fixed.

**F-057. A room with no host stays without one.** Not graded. `RoomSlots.Seat` seats a player but grants no host
role, and `LeaveSeat` hands the host on only to a player still seated. After the host leaves an otherwise empty room
and joins again, `GET /v1/rooms` shows `host: null` and nobody can start a round from the game.

**F-060. A round whose only player failed to load never ends, and the room shows the player nothing.** Not graded. No
rule in `Basil.Domain/Multiplayer/Room/RoomRounds.cs` ends a round whose players never load or leave the play; only an
abort by the creator ended it (`!mp abort` answered "Aborted the match" and "Match aborted." for the same action). On
the 2026-11-18 screenshot the seated player's own slot row was drawn empty, probably linked to F-058.

**F-040. Spectating: one score per bundle on the wire, and bundles that are not play are dropped.** Not graded. The
osu! wire carries one score frame per bundle, so the API can carry a score per bundle at most, unless the server scores
the frames itself (a large feature). `Basil.Host.Stable/Packets/PacketHandlers.Spectating.cs` drops every bundle whose
action is not `Standard` (new song, skip, completion, fail, pause, unpause, song select) before the API sees it. The
owner chooses per-bundle pairs or server-side scoring; forward every action either way.

**F-041. Spectating through the API: oneself is refused, and the 409 is misleading.** Not graded, requested by the
owner. `Session.Spectate` (`Basil.Application.Sessions/Objects/Session.cs`) answers `Self` when the spectator is the
player. `GET /v1/users/{id}/spectate` answers 409 `targetOffline` "The player is not in game." when the player has no
open osu! client, although the player may be online and not playing. The owner wants spectating allowed when the player
is not playing and on oneself, a self spectator not shown in the osu! client, and the stream refused or ended only when
the player is offline.

**F-042. The spectate stream mixes play and activity in one event.** Not graded, requested by the owner, frozen
contract (D2). `Basil.Host.Rest/Sse/SpectateRoutes.cs` sends frames (`type: "frames"`) and status items (`type:
"status"`) in the same `bundle` event. The owner wants two events: the current bundle renamed `replay`, and a separate
`activity` event.

**F-059. The client's error reports are thrown away.** Not graded. `POST /web/osu-error.php` has no route in
`Basil.Host.Stable/Web/OsuWebRoutes.cs` and answers 404; it is the only place the server could learn why a client
failed. Accept the report and log it.

**F-064 (osu! side, see Documentation).** The osu! login page still describes a hardware-ban check.

### IRC and BasilBot

Owner: F-005 to F-016 are all blockers. Reply texts are in `Basil.Application.Bot/Commands/*Replies.cs` and
`Basil.Host.Irc/Support/IrcReplies.cs`.

**F-006. A user with no role can target a private room and read its settings.** Blocker, security. `!mp in <id>`
(`Basil.Infrastructure.Bot/Handlers/Commands/Mp/MpCommands.Lifecycle.cs`) sets the target after only `lobby.Find`, and
`SettingsAsync` prints name, creator, mode and mods with no read check, although the channel answers `473` and the
API answers 404 to the same user. Both must follow the rule of reading the room channel.

**F-008. Commands that answer nothing.** Blocker. Unknown commands in a private message are now documented as
unanswered (`Basil.Application.Bot/BotReference.cs`: "Unknown commands are not answered."), which the owner has not
accepted as the answer. Not re-tried: `!mp timer` and the first `!mp aborttimer` in a private message (the marks go to
`#mp_<n>`, which the typist may not have joined), and `!mp close` in the room channel (confirmed only by the `KICK`).

**F-009. Replies that say something else than what happened.** Blocker. Current texts that still mislead:
`MpReplies.CreatedMatch` ends "...and have been added as a referee" (the creator is not a referee, `AGENTS.md`
Authority); `MpReplies.NoModChanges` is "No mod changes" for a mod that does not exist; `BotReplies.RollResult` is
"{user} rolls {points} point(s)" and ignores a bad argument; `!help mp` ignores its argument; the delayed
`!mp start 3` answers `AnnouncementReplies` "Queued the match to start in {seconds} seconds" before the refusal
"Match is already in progress."/no beatmap; `MpReplies.InvitedToRoom` "Invited {player} to the room" for a player with
no game client; `MpReplies.TargetNotOnline` "That player is not online." where `NAMES` shows the player online (F-011);
`!mp size 0` answers the usage line; `BotReplies.WhereIsIn` "{name} is in {country}" prints "Unknown" as a place.

**F-010. One situation, several wordings.** Blocker. Changed in part: the refusal for lack of privileges is now one
text on `!mp` and `!channel`, "You do not have the privileges needed for that.", but it still names no role (D4). An
unknown user is still "User not found" (`mp.userNotFound`), "User is not registered." (`mp.userNotRegistered`) and
"{name} is not registered." (`bot.notRegistered`); the room is still a "match" in BasilBot and a "room" elsewhere;
full stops are still mixed.

**F-011. An API session still joins the chat channels.** Blocker. The owner decided that an API session is not a chat
presence. `GeneralChannelRegistry.JoinAutoChannels` (`Basil.Application.Chat/Registry/GeneralChannelRegistry.cs`)
joins every opened session, API included, so `NAMES` and `ISON` show a player who only holds a token, and the session
ends later with "Ping timeout". The reason a session leaves must also be true, and `!mp host` must agree with `NAMES`.

**F-012. The creator is not told to join the room channel.** Blocker. After `!mp make` over IRC the reply says only
"...You're now targeting it..."; `LIST` shows `#mp_<n> 0` and the creator must `JOIN` by hand.

**F-013. `!channel list` prints internal values.** Blocker. `ChannelReplies` formats
`{name} read={read} write={write} autojoin={autoJoin} visible={visible} topic={topic}` with numbers and `True`; use
privilege names and `yes`/`no` (also F-053).

**F-014. `!mp settings` shows less than its help line promises.** Blocker. The help says "match id, map, team type, win
condition, mods, and slots"; `SettingsAsync` prints name, beatmap, team mode and win condition, active mods when set,
creator, players and slots, but no size, host, referees, lock, or private and password state.

**F-015. `irc.md` and the server disagree.** Blocker. `docs/for-developers/irc.md:162` says an announcement from
BasilBot is a `NOTICE`; the countdown marks arrive as `PRIVMSG #mp_<n>`. The doc says the `404` text "names the
reason"; the text is always `IrcReplies.CannotSend` "Cannot send to channel", and `473` is always "Cannot join
channel". Decide which side changes; naming the reason reveals nothing the numeric does not.

**F-016. Small things a user sees.** Blocker. `QUIT` without a reason is echoed as "Quit:"
(`IrcCommands.cs:77`); `002` says "running version basil-1" (`IrcReplies.Version`) instead of the release version;
`422 :MOTD File is missing` is sent on every sign-in when no message of the day is set (`IrcCommands.cs:207`);
`!mp help` is still one message per command (32 `mp` entries in `CommandCatalog`).

**F-017. One idle timeout for every connection but the API.** Not graded. Changed: an API session now expires after 8
hours and a new sign-in of the same type may replace a silent session after 30 seconds
(`Basil.Domain/Sessions/SessionRules.cs`); every other session still expires after 300 seconds of silence, swept
every 100 seconds. A crashed game client keeps its slot and channels for up to six and a half minutes. The owner asked
whether five minutes is too long; the per-kind values still need a decision.

**F-018. Irssi shows a server error on every connection and every join.** Not graded. `MODE <nick> +i` is answered
`501 :Unknown MODE flag` and `MODE #channel b` is answered `482 :Channels are managed through the API or BasilBot, not
through IRC` (`IrcCommands.Messaging.cs`, `Mode`); both are printed in the user's window. Answer what a client's own
housekeeping expects (`221` for a user mode request, an empty ban list `368`) and keep `482` for a real change.

**F-019. "Match #n" names a room number that is reused.** Decided by the owner: rooms and matches use one number on
every surface (`#mp_<n>`, `/v1/rooms/<n>`, `/v1/matches/<n>`, BasilBot's replies). Today `RoomView`
(`Basil.Host.Shared/Views/RoomViews.cs`) still carries both `Id` and `MatchId`, BasilBot calls the live room "the
match #n", and `GET /v1/matches/{id}` takes the match number. The dashboard's Lobby tab and closed list show the same
room under two numbers (opened as 1, listed as 14). Frozen contract (D2).

**F-043. A failed IRC command is logged and never answered.** Not graded. The key lockout is gone with IRC keys (IRC
now signs in with the account password), but `IrcListener` still logs `IRC command {Command} failed` and sends the
client nothing when a command throws, for example a sign-in during a database outage.

### HTTP API and SSE

Owner: F-021 to F-031 are all blockers. Routes are in `Basil.Host.Rest/Routes/` and `Basil.Host.Rest/Sse/`.

**F-021. No checked-in OpenAPI document, no Postman collection, no contract check.** Blocker. Changed: the stale copy
and the collection were removed with the tests; the `rest-contract` job of `.github/workflows/ci.yml` still builds,
starts the server and publishes the served document, but its check and its Postman run are commented out. Remaining:
decide whether to restore a checked-in document and a collection (D10 ships one), and re-enable the check. `ci.yml`
runs on `main`, `master` and pull requests only.

**F-022. The OpenAPI document describes no answer and no room-command body.** Blocker, frozen contract. No route
declares `Produces`; every answer is the generic envelope. The 24 room commands
(`Basil.Host.Rest/Routes/RoomRoutes.cs`, `Command`) read their body by hand with no `Accepts` and have a summary but
no description, so Scalar shows nothing to send. `OpenApiSetup.cs` adds generic 401, 403, 404, 409, 422 and 429
responses to every route, wrong for some (`GET /health`).

**F-023. A wrong room-command body is answered "not found".** Blocker. A missing field is read as user 0
(`{"id":3}` gives 404 `notFound`); `{"user":"bob"}` gives 422 "The body is not valid." without naming the field. A
missing or mistyped field must be a 422 that names the field; the owner decides whether the API accepts a name as
BasilBot does.

**F-024. Most refusals repeat their code instead of explaining.** Blocker. `OutcomeResults.Refusal`
(`Basil.Host.Rest/Http/OutcomeResults.cs`) answers `Api.Error(status, code, code)`: `message` is the code itself for
every outcome (`privilegeDenied`, `roleDenied`, `notSelf`, `noTeams`, `targetOffline`, `invalidSettings`, ...), against
`docs/for-client/api/response-envelope.md` which defines `message` as a human-readable description. The same code has
two texts (`notSelf`). Every error needs a sentence, the one BasilBot uses for the same outcome, and a refusal names
the role that can act (D4).

**F-025. Privileges have three forms.** Blocker, frozen contract. `UserView` sends `ulong Privileges` and
`ulong EffectivePrivileges`, `ChannelView` sends `byte ReadPrivileges` and `byte WritePrivileges`, settings answer
`"player, supporter"`, and the request side takes `UserPrivileges` as text or number. One form everywhere (see F-082).

**F-026. The state of the target is checked before the caller's right to act.** Blocker. Unchanged since 2026-11-17:
as a user with no role, `PUT /v1/faqs/{entry}`, `POST /v1/announce`, `PUT /v1/users/{id}/password` and
`POST /v1/users/{id}/sessions/{type}` answer a 422 for the body before any 403; room `host` and `invite` answer 409
`targetOffline` and `map` 409 `noBeatmap` to an outsider; `PATCH /v1/settings/{category}` is 404 for an unknown
category and 403 for `general`; `PATCH /v1/beatmapsets/{id}` looks up before it authorizes. `working-notes.md`
("Authorize before you look up") states the rule.

**F-027. Answers that claim success when nothing happened.** Blocker. `PATCH /v1/users/{id}` with `{}` answers 200
"Updated successfully"; `POST /v1/rooms/{id}/start` with `{"seconds":3}` and no beatmap answers 200 "Operation
successful" for a countdown that cannot end in a start; room commands answer "Operation successful" with `data: null`,
so a tool cannot show what changed. Refuse what cannot happen when it is asked, and answer a room command with the
room as it now is.

**F-028. One missing thing, three wordings.** Blocker. For a missing beatmapset `/background`, `/audio` and `/video`
answer "No such beatmapset." and `/audiopreview`, `/download` and `/storyboard` answer "No such file."; for a missing
beatmap `/v1/beatmaps/{id}` says "No such beatmap." and its files say "No such file." (`BeatmapRoutes.cs`). Say which
thing is missing.

**F-029. `AGENTS.md` and the stream routes disagree.** Blocker. `AGENTS.md` ("SSE") says live streams use dedicated
`/live` routes; four of the five stream routes do not (`/v1/matches/{id}`, `/v1/users/{id}/spectate`,
`/v1/diagnostics`, `/v1/diagnostics/{category}`), and `GET /v1/matches/{id}` is a stream only. The owner decides
whether the rule or the routes change; `AGENTS.md`, `docs/for-developers/sse.md` and `docs/for-client/api/sse.md`
agree before `/v1` is frozen.

**F-030. A player cannot list the matches they took part in.** Blocker, business rule too strict (candidate).
`GET /v1/matches` is "For room managers only" (`Basil.Host.Rest/Sse/MatchRoutes.cs`); the report of one's own match
is readable by id. The owner decides whether the list shows each caller the matches they may view.

**F-031. `response-envelope.md` is wrong in places.** Blocker. `docs/for-client/api/response-envelope.md` line 80
says `200` with `data: null` replaces `204` (`sse.md` documents a 204); line 109 links the removed `ADR-009`; line 111
says a body that is not JSON is `400` (the server answers `422 "The body is not valid."`); lines 9 and 217 exempt
"`/live` streams" while four of five do not end in `/live`; line 178 ("Sets of privileges and privileges are
bitmasks") is garbled.

**F-032. Room commands through the API: answers that say something else than what happened.** Blocker (same list as
F-009 for the API). `mods` with an unknown mod, `name` of 80 characters (cut to 50 without a word) and `invite` of a
nonexistent user (`409 targetOffline`) answer success or the wrong reason; a second `aborttimer` is `409 notInProgress`
(the code speaks of a round); `start` with no body is `422 "A JSON body is required."`; `invalidSettings` does not say
which value or what range; `kick` of a referee is `403 isManager`, a room rule answered as a missing privilege.

**F-067. The generated API reference leaves routes undescribed.** Blocker. About 85 operations carry a summary and
about 60 a description (re-counted by `WithSummary`/`WithDescription`); none of the room commands, `POST
/v1/auth/logout`, `DELETE /v1/beatmapsets/{id}`, `GET /v1/scores/{id}` and others have one. Few descriptions follow the
order of `AGENTS.md` rule 5; `POST /v1/settings/ruleset/update` describes its mechanism. `GET /v1/users/{id}/sessions`
takes "a bitmask of the session types" without the values (F-053). The BasilBot guide
(`Basil.Application.Bot/BotReference.cs`) has no example or privilege column; the IRC guide
(`Basil.Host.Irc/Clients/IrcReference.cs`) has no usage line or example.

**F-082. API views send numbers and text where the contract has an enum.** Blocker. See F-025; also `string Mods` in
`ScoreViews.cs` and `RoomViews.cs` (likely deliberate for a flags enum, the contract should say so) and
`ulong Privileges` in `Basil.Host.Cli/Dashboard/Data/DashboardModel.cs`.

### Operation, console and Docker

**F-034. A mistyped shell command starts a second server against the same database.** Not graded, data safety.
`ShellRunner.IsCommand` (`Basil/Lifetime/ShellRunner.cs`) returns false for any first argument that is not a known
command, so `Basil nosuch` and `Basil --help` run the full startup (clean-up of "unfinished" matches and sessions,
BasilBot online) against the live database, then fail on the busy port. An argument that is not a known command or
option must be refused before anything starts, and `--help` must print help.

**F-035. Without the control socket, shell commands half work and one says the server is down.**
`Basil.Host.Cli/Socket/ControlSocket.cs` keeps `MaxPathLength = 100`; beyond it the server runs without the socket
and `Basil rooms list` answers "error: serverNotRunning: The server is not running; this command needs it."
(`ShellRunner.cs:47`). Use a path that always fits (or a setting), and say that the server could not be reached.

**F-036. The shipped configuration logs every request.** Not graded. `Basil/Configurations/appsettings.json` sets
`Logging:LogLevel` `Default`, `Microsoft`, `Microsoft.Hosting.Lifetime` and `System` to `Trace`, against
`docs/for-developers/logging.md` ("Nothing logs each osu! (stable) packet, IRC line or REST request") and
`docs/for-technicians/logging.md` (`Information`). Ship `Information` for Basil and `Warning` for the framework.

**F-037. One log per session, apart from the system log.** Requested by the owner. Today one rolling file
`Logs/basil-*.log` holds everything. To decide: what a session is here (one connection, or an account's whole sign-in),
what a session log holds, how long it is kept, and how it relates to the "lifecycle, not routine traffic" rule.

**F-038. Smaller things an operator sees.** Not graded. Still true: `docs/for-technicians/console.md` ("Modes")
describes `--console 0` as "Log only ... Changes the server: no" although it accepts commands; no startup line says
where IRC listens (`IrcListener` logs nothing at start); `users create --types` and `--privileges` help say "as a
bitmask" (F-053); the command box refuses `users alice` ("Unknown command", ids only); `users list` is wider than 160
columns; the Users footer says `show 1–6 in 9` with seven rows (F-076); the Sessions tab groups read `Irc` and `Api`;
every console error shows the internal code first (`error: invalid: ...`, `CommandOutput.cs`). The shutdown reason is
fixed (`SessionEndReason.ServerStopped`).

**F-046. The Configuration page does not show the effective configuration.** Not graded. Settings › Configuration
lists the values of the file, not what the server runs with (environment variables, command line), and masks the
certificate path. Show the effective value of every key and where it came from; mask only secrets.

**F-047. Settings show raw values.** Not graded. Sizes in bytes (`Largest beatmapset archive 104857600`), durations as
