## Cli, operation and logging (part 1)

Tried on 2026-11-17: the server stopped with Ctrl+C from `--console 0` while an IRC client was connected, restarted with
the dashboard (`--console 1`, tmux 160×45), the tabs captured, commands typed in the command box, and console commands
run from a shell while the server ran. What worked: the graceful shutdown and its IRC notice
(`NOTICE :Server is shutting down`, then `ERROR :Closing Link`), every shutdown step logged, `help <group>`, room and
user commands by id, the silence and its end.

**[F-034] A mistyped shell command starts a second server against the same database**
Category: operation, data safety. State: verified for the behaviour, likely for the damage.
Evidence: with the server running, `Basil nosuch` and `Basil --help` are not refused as unknown commands: the process
starts a full server, logs `BasilBot is online`, `Closed 0 unfinished matches`, `Closed 0 connections left open`, then
fails with `System.Net.Sockets.SocketException (98): Address already in use` and a stack trace; exit code 134.
Failing situation: an operator who mistypes a command, or asks for help, runs the startup clean-up of a second server
(closing "unfinished" matches and "left open" connections, bringing BasilBot online) against the database of the live
server.
Proposal: an argument that is not a known command or option is refused before anything starts; `--help` prints help.
Effort: S. Decision: —

**[F-035] Without the control socket, shell commands half work and one says the server is down**
Category: operation, experience. State: verified.
Evidence: with a data directory deeper than 100 characters the server logs
`ERR The control socket path is longer than 100 characters, so the server runs without it` and goes on. From a shell,
`Basil rooms list` then answers `error: serverNotRunning: The server is not running; this command needs it.` while the
server is running; `Basil users 5` and `Basil users 5 unsilence` run against the database directly.
Failing situation: an operator who keeps data under a long path (a mount, a container volume) loses the shell
commands that need the live server and is told the server is down.
Proposal: a socket path that always fits (or a setting for it), the reason and the fix in the error, and a message
that says the server could not be reached rather than that it is not running. Effort: S. Decision: —

**[F-036] The shipped configuration logs every request, against the logging design**
Category: operation, documentation. State: verified.
Evidence: `src/Basil/Configurations/appsettings.json` sets `Logging:LogLevel` `Default`, `Microsoft` and `System` to
`Trace`. Every HTTP request writes five `INF` lines to the dashboard console (`Request starting`, `Executing endpoint`,
`Setting HTTP status code`, `Writing value`, `Executed endpoint`) and many `DBG`/`VRB` lines to the file: 1 MB in 50

## Event system, chat latency and spectating

Reported by the owner on 2026-11-17 and traced in the code the same day. Live measurement was not possible: the Docker

**[F-039] Chat takes 3 to 5 seconds in both directions; every event of the server waits in one serial queue**
Category: performance, correctness. State: reported by the owner; cause likely (code read, not measured).
Evidence: since `bc193a93` (2026-10-27) every event is published through `QueuedNotificationPublisher` into one
`EventQueue` (`src/Application/Shared/Events/EventQueue.cs`) with one reader that runs every handler of every event one
after the other. Before it, each event category had its own `EventBus<T>` with its own reader, so chat never waited
behind rooms or users. On that one queue:

* each chat message is delivered by `Host.Stable` `MessageDelivery` and `Host.Irc` `MessageDelivery`, and each calls
  `Channel.RecipientsAsync` (`src/Application/Chat/Objects/Channel.cs:91-108`), which reads the relationships of every
  member of the channel from the database, one query per member, uncached (`EfRelationshipRepository.ListAsync`):
  2 × members queries per message;
* every status change of an osu! client awaits `GetUserStats` (`src/Hosts/Stable/Delivery/UserDelivery.cs:54-57`),
  and the client changes status on every song selection;
* every room event awaits a database write in its recorder (`src/Infrastructure/Multiplayer/Handlers/*Recorder.cs`).

The owner sees the message appear at the server and at the client at the same moment; the dashboard's chat feed
(`ChatFeedHandler`) is on the same queue, which fits a delay in the queue rather than in a transport.
A second, smaller delay is likely in the osu! host: `StableRoutes` drains a client's outbox right after dispatching the
packets of its poll (`src/Hosts/Stable/Routes/StableRoutes.cs:98-99`), while the deliveries those packets cause run
later on the queue, so a poll never carries the result of its own request; it waits for the next poll.
To verify: the Monitor's `events pending` while chatting, and `<scratch>/latency.py` with and without players.
Proposal (for the owner): chat delivery must not wait behind slow handlers; options are a reader per event category
as before, blocks kept in memory, or handlers that never await I/O on the shared queue. Effort: M. Decision: —

Measured on 2026-11-17 after the database came back, on an idle server: IRC to IRC 2 to 5 ms (channel and private
message, `<scratch>/latency.py`); IRC to a simulated osu! client polling every 50 ms 10 to 52 ms

refused, which led to F-045.
