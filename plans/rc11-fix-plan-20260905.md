# RC11 fix plan — observability, logging reform, and mechanism confirmation

Companion to [`rc11-recurrence-analysis-20260905.md`](rc11-recurrence-analysis-20260905.md), which
holds the evidence. Branch: `chore/perf-investigation`. Baseline commit: `5bde7b5`.

## Implementation outcome (2026-09-05, same day)

Phases 1, 3, 4, and 6 were implemented and verified (full 1597-test suite passing, Release build
clean). Phase 2's re-run used a new API-only profile (`Profiles/api-only.json`) per an explicit
scope-narrowing request, rather than the full `login → idle → chat → multiplayer → api` sequence
this document specifies — **the API-only run did not reproduce the collapse** (max ThreadPool queue
746 vs. 2004; max threads 61 vs. 517; zero CPU-near-zero-with-high-threads samples). Per this
document's own ordering rationale, Phase 2b (reading a thread dump) and the conditional half of
Phase 5 (the SQLite-specific fix) were therefore skipped rather than guessed at — there was no dump
to read. The user chose, when asked, to proceed with Phases 3–6 and record RC11's mechanism as still
open rather than block further on a second, larger reproduction attempt.

The corrected timeline, the logging defects (now fixed), and the full "what changed" table live in
[`known-limitations.md`](../docs/for-developers/known-limitations.md)'s RC11 entry — that document
is now authoritative for RC11's status; do not let this plan's original text be read as current.

**Open decision #5 (header case-sensitivity) was resolved by implementation, not by an explicit
answer.** Phase 3.5 shipped as designed: `RequestIdLoggingMiddleware` and `BanchoProtocolRoutes` now
read the three IP headers through `IHeaderDictionary`'s own case-insensitive lookup instead of a
case-sensitive `Dictionary` built from `ToDictionary(...)`. This is a real behavior change on the
login path — a client sending `x-forwarded-for` in lowercase, previously silently ignored, is now
honored — bundled into what was framed as a pure allocation fix. It was not separately confirmed with
the user before shipping; flagging it here so it is a known, deliberate change rather than a silent
one.

**The async-sink change was verified under real load before this document was closed out**, per a
short follow-up run (`Profiles/verify-async-sinks.json`, deleted after use): 500 concurrency against
`/health` and `/users/{id}` for ~25s each with `Basil:Logging:MinimumLevel=Debug`. Result: 411,766
`Debug`-level request lines all landed correctly with no gaps, the last line's timestamp lines up
exactly with the scenario's own measured-duration end, and neither the server log nor the harness log
show any warning or dropped-event signal. This also re-exercised Phase 4's `DrainAsync` against a live
child process without incident. Not separately tested: dispose-time flush behavior when the async
queue has a genuine backlog at the exact moment of an abrupt process kill — that path is Serilog's own
library behavior, not custom code, and was judged out of scope to construct a test for here.

The rest of this document is preserved as originally written, for the reasoning behind each phase.

---

## Goal

Two outcomes, in this order:

1. **Know** why the server stopped at 10:56 UTC — not "which family of explanations is plausible".
2. **Fix** the logging pipeline so it is correct on its own merits, and so no future investigation
   loses its evidence to the same defaults.

## Success criteria

| # | Criterion | How it is verified |
|---|---|---|
| 1 | The blocking mechanism is named from a stack, not inferred | Thread dump taken during the collapse window shows where ≥ 400 threads are parked |
| 2 | A `full.json` run produces a complete application log covering the whole run | Log files present, rolled, none truncated; last event timestamp ≥ run end |
| 3 | No log write can block a request thread | Sinks are async-wrapped with a bounded queue that drops rather than blocks |
| 4 | A successful HTTP request produces no Information-level log event | `full.json` re-run's log contains zero `API request completed … -> 2xx` lines at the default level |
| 5 | The existing suite still passes and Release builds clean | `dotnet test` (1597 tests), `dotnet build -c Release` |

## Non-goals

* Making any particular concurrency number pass. The project's stated aim is a capacity envelope, not
  an "N users" target.
* Changing bancho packet behaviour, session behaviour, or API response schemas. None of the work below
  touches an externally observable contract except log text, which
  [`testing.md`](../docs/for-developers/testing.md) explicitly excludes from pinned contracts.
* Rewriting the SQLite access layer. That is gated on Phase 2's result.

---

## Ordering rationale — read before reordering

The logging reform (Phase 3) would very likely *make the collapse go away*. If it lands before the
thread dump is taken, the investigation ends with a working server and no explanation, and both
Candidate A (console sink blocking on the harness pipe) and Candidate B (synchronous SQLite) stay
open forever.

So the sequence is deliberately:

```
Phase 1  observability only, single variable, does not touch the console path
   ↓
Phase 2  re-run + thread dump          ← the mechanism is named here
   ↓
Phase 3  logging reform                ← lands regardless of what Phase 2 says
   ↓
Phase 4  harness fix
   ↓
Phase 5  mechanism-specific fix        ← contents decided by Phase 2
   ↓
Phase 6  documentation
```

If the mechanism turns out to matter less than getting a healthy server back, Phases 3–4 can be
pulled forward — but then Phase 2 must be dropped explicitly and RC11's mechanism recorded as
permanently unknown, rather than quietly assumed closed a second time.

## Phase 1 — Observability only

One change, chosen because it does not perturb either candidate mechanism: it alters the file sink,
not the console path, and not the request path.

### 1.1 Bound and roll the file sinks

`src/Basil.Web/Program.cs:306-318`. Both `WriteTo.File` calls currently pass neither
`fileSizeLimitBytes` nor `rollOnFileSizeLimit`, so each silently stops at Serilog's 1 GB default.

Add to both sinks:

* `fileSizeLimitBytes` — an explicit value (proposed: 256 MB, so a stalled tail or a runaway logger
  is visible as many files rather than one truncation)
* `rollOnFileSizeLimit: true`
* replace `retainedFileCountLimit: 30` with `retainedFileTimeLimit: TimeSpan.FromDays(30)` — with
  size-rolling in play, a *count* of 30 no longer means 30 days, which is what both
  [`for-developers/logging.md`](../docs/for-developers/logging.md) and
  [`for-technicians/logging.md`](../docs/for-technicians/logging.md) promise

Confirm these parameter names against `Serilog.Sinks.File` 7.0.0 at implementation time.

**Interaction to check:** `HardLinkFileLifecycleHooks.OnFileOpened` recreates `latest.log` on every
file open. With size-rolling it now also fires mid-day. The hook already handles this correctly —
its XML doc says "daily rollover or process start" and will need one sentence updated in Phase 6.

**Verify:** run any short load profile that exceeds 256 MB of log; confirm multiple rolled files
exist, `latest.log` points at the newest, and no file is truncated at its limit.

## Phase 2 — Name the mechanism

### 2.1 Re-run `full.json` with a dump captured at the collapse

Re-run the same profile. The collapse is reliably reachable: it landed in `api_user_500`, roughly
70 minutes into the run, immediately after `api_health_500`.

Capture, during the window where `resources.csv` shows CPU ≈ 0 with a rising ThreadPool queue:

```
dotnet-dump collect -p <server pid>
# then, in dotnet-dump analyze:
clrstack -all
```

`dotnet-stack report -p <pid>` is an acceptable lighter-weight substitute.

Practical notes:

* Watch `ThreadPoolQueueLength` in `resources.csv` live; trigger the dump once it passes ~1000 while
  `CpuPercent` is below 1.
* **The window is forgiving.** In this run it ran 10:56 → 11:02 — six minutes. The trigger does not
  need to be precise.
* **The dump may end the run, and that is acceptable.** `dotnet-dump collect` against a process with
  ~490 threads and a ~900 MB working set takes real time and suspends the runtime while it writes.
  The dump *is* the deliverable; the remaining scenarios are already measuring a collapsed server and
  produce no usable capacity data.
* **Preserve `resources.csv` alongside the dump.** The dump alone does not establish *when* it was
  taken; the resource sample at that timestamp is what proves it was captured inside the collapse and
  not during recovery or teardown.
* Take the dump *before* the harness tears the process down at the end of the run.
* Store both next to the run's report folder.

### 2.2 Read the verdict off the stacks

| Where the ~488 threads are parked | Conclusion | Phase 5 becomes |
|---|---|---|
| `ConsoleSink.Emit` → `Console.Out.Write` → `WriteFile` | Candidate A confirmed | Phase 3 alone is the fix; Phase 5 is only the outbox item |
| `sqlite3_step` / SQLite busy handler | Candidate B confirmed | Phase 5 = bound concurrency on the database path |
| Neither | Both candidates dead | Phase 5 is rewritten from the stacks |

**This step is the pivot of the whole plan.** One dump replaces every remaining line of tracing.

### 2.3 Cheaper corroboration, if a dump proves impractical

Re-run `full.json` with `.WriteTo.Console` removed as the single changed variable. If the collapse
disappears, Candidate A is confirmed by intervention. This is weaker than a dump — it shows *that*
logging is involved, not *where* — but it is decisive between A and B.

## Phase 3 — Logging reform

Lands regardless of Phase 2's outcome. Every item below is a CONFIRMED defect in its own right.

The project's own [`for-developers/logging.md`](../docs/for-developers/logging.md) already states the
policy the code violates:

> "For example, successfully handling an HTTP request is not itself a domain event."

> "Do not compensate for a missing log level by logging everything at `Information`."

This phase enforces the existing policy rather than inventing a new one.

### 3.1 Never let a log write block a request thread

Add `Serilog.Sinks.Async` to `Directory.Packages.props` and wrap both the console and file sinks:

```csharp
.WriteTo.Async(a => a.Console(...))
.WriteTo.Async(a => a.File(...))
```

Behaviour this buys: log events go to a bounded in-memory queue drained by one background thread. On
overflow the default is to **drop**, not block — which is the property required here. A request
thread can never again be parked inside a sink.

Decision to make explicitly: overflow is silent by default. `Serilog.Sinks.Async` accepts a `monitor`
callback for queue depth. Recommendation: take the default drop behaviour and document it, rather
than adding monitoring infrastructure with no consumer yet.

This is the change that removes Candidate A's mechanism, which is why it must not land before
Phase 2.

### 3.2 Stop logging successful requests at Information

`src/Basil.Web/Middleware/ApiRequestLoggingMiddleware.cs:35-41` logs one Information line per
completed `basilapi` request unconditionally. This produced ~3.07 million lines — about 80 % of the
gigabyte — the overwhelming majority of the form `GET /health -> 200 in 0 ms`.

Level the event by outcome instead:

| Status | Level |
|---|---|
| `< 500` | `Debug` |
| `>= 500` | `Warning` |

The middleware stays — a per-request API audit trail is worth having on demand. It simply stops
being on by default. Anyone who needs it sets `Basil:Logging:MinimumLevel` to `Debug`.

Deliberately out of scope, to keep the change minimal: a "slow request" threshold that promotes a
long request to `Warning`. Worth considering later; it is new behaviour, not a defect fix.

### 3.3 Remove `UseSerilogRequestLogging()`

`src/Basil.Web/Program.cs:167`. Its events are tagged `FallbackCategory` by `CategoryEnricher` and
dropped by the filter at `Program.cs:301-304`. The 1 GB log contains zero of them.

So it builds, enriches and filter-evaluates one log event per request and throws all of them away.
Worse, the suppression is accidental — `MinimumLevel.Override("Microsoft.AspNetCore", Warning)` at
line 296 does not cover it. Adding a `Basil.Web.` rule to `CategoryEnricher` would silently
resurrect a second per-request log line.

Removing it also drops the `Serilog.AspNetCore` request-logging dependency surface; the package is
still needed for `AddSerilog`.

### 3.4 Level security-relevant admin auth correctly

`src/Basil.Web/Auth/…:58,62`:

* `Admin auth succeeded: Path={Path}` — currently `Information`, fires on **every** authenticated
  admin request → `Debug`.
* `Admin auth failed: Path={Path}` — currently `Information`. This is an abnormal, security-relevant
  condition → `Warning`, matching the level table in `logging.md`.

### 3.5 Stop materialising the header collection on every request

The same pattern appears at two call sites, both feeding `Geolocation.PhraseIpAddress`:

* `src/Basil.Web/Middleware/RequestIdLoggingMiddleware.cs:23` — runs on **every request on every
  host group**
* `src/Basil.Web/Routing/Bancho/BanchoProtocolRoutes.cs:136` — runs once per bancho login

```csharp
var headers = request.Headers.ToDictionary(h => h.Key, h => h.Value.ToString());
```

Each allocates a dictionary sized to the whole header collection plus one string per header value.
At the 15,229 req/s this run reached, the middleware site alone is roughly 15k dictionaries and well
over 100k strings per second.

**What actually constrains the fix.** `Geolocation.PhraseIpAddress`
(`src/Basil.Domain/Login/Geolocation.cs:15-22`) reads exactly three keys, and reads two of them with
a bare indexer:

```csharp
if (headers.TryGetValue("CF-Connecting-IP", out var cfIp)) return IPAddress.Parse(cfIp);
var forwards = headers["X-Forwarded-For"].Split(',');
var ipStr = forwards.Length != 1 ? forwards[0].Trim() : headers["X-Real-IP"];
```

So it throws `KeyNotFoundException` unless `X-Forwarded-For` **and** `X-Real-IP` are both present.
Both call sites guarantee that with an identical synthesize block that writes both together when
neither forwarded header arrived — `RequestIdLoggingMiddleware.cs:25-30` and
`BanchoProtocolRoutes.cs:141-149`, the latter carrying a comment explaining that both must be
synthesized together because `PhraseIpAddress` falls back to `X-Real-IP` whenever `X-Forwarded-For`
holds a single entry.

`BanchoProtocolRoutes.cs:158` is on the login path that the 2026-08 investigation traced a
missing-`cho-token` symptom to. It cannot be allowed to start throwing.

**The design, one option only.** At both sites, build the dictionary from just the three keys
`PhraseIpAddress` reads, instead of from the whole header collection. `PhraseIpAddress`'s signature
and behaviour are unchanged; the synthesize block at each site stays exactly as it is and keeps
providing the two keys the bare indexers need. Neither site uses `headers` for anything else —
verified: the only references are the `ContainsKey` guard, the two synthesize writes, and the
`PhraseIpAddress` call.

No shared helper is introduced. Two call sites with a four-line dictionary build do not justify a new
abstraction, and the login path is not somewhere to add indirection while chasing an allocation.

**Deliberate behaviour change, flagged rather than silent.** `IHeaderDictionary` compares keys
case-insensitively; the `Dictionary<string, string>` produced by `ToDictionary` uses the default
ordinal comparer and so compares case-**sensitively**. Today a client sending `x-forwarded-for` in
lowercase therefore fails the `ContainsKey("X-Forwarded-For")` guard and gets its real forwarded
header ignored. Reading the three keys through `request.Headers` fixes that, because the lookup then
goes through the case-insensitive collection.

That is a correctness improvement — HTTP header names are case-insensitive — but it *is* a behaviour
change on a login path, so it is called out here for an explicit decision rather than slipped in as a
side effect of a performance fix.

**Verification.** Confirm before editing whether the existing suite pins `PhraseIpAddress`'s
precedence (`CF-Connecting-IP` → first entry of a multi-value `X-Forwarded-For` → `X-Real-IP`). If it
does not, add a regression test for that precedence *before* touching either call site — this is the
one change in the plan that can turn a live request into a 500.

### 3.6 What is explicitly *not* changed

The 86 `LogInformation` call sites were inventoried. Almost all are genuine low-frequency domain
lifecycle events — match created/closed, user registered, admin actions, IRC connect, startup banner
— and are correct at `Information` under the existing policy. They are not touched.

The login/logout and match join/leave events (`LoginService.cs:323`,
`PlayerLogoutService.cs:45`, `MatchMembershipService.cs:354,417`) accounted for the first ~100 MB of
the log. That is an artefact of a 5,000-account load test, not of a real tournament, and they are
legitimate domain events under the policy. **Not changed** — flagging them here so the decision is on
the record rather than silently deferred.

## Phase 4 — Load-test harness

`tests/Basil.LoadTests/Hosting/DotnetServerHost.cs:81-82`:

```csharp
_ = _process.StandardOutput.ReadToEndAsync(cancellationToken);
_ = _process.StandardError.ReadToEndAsync(cancellationToken);
```

Two problems, independent of whether Candidate A is confirmed:

* `ReadToEndAsync` accumulates the entire run's stdout in harness memory and never releases it. This
  run pushed well over a gigabyte through it.
* The task is discarded, so any failure inside the drain is invisible.

Replace with a discarding drain that does not accumulate — read into a reusable buffer and throw the
bytes away — and observe the task's completion so a fault surfaces.

Rationale for doing this at all: the apparatus must not be able to block the subject it measures.
Even if Phase 3 makes it harmless, a load harness that can stall the server under test invalidates
every future measurement.

## Phase 5 — Mechanism-specific fixes

### 5.1 Conditional on Phase 2 — database path

Only if the dump shows threads parked in SQLite.

`src/Basil.Infrastructure/Persistence/SqliteConnectionFactory.cs:19-27` opens synchronously —
`connection.Open()` plus a `PRAGMA` round-trip via `ExecuteNonQuery()` — from inside `async`
repository methods, at 21 call sites. `Microsoft.Data.Sqlite` has no true async I/O, so every
database call occupies a ThreadPool thread for its full duration; with `busy_timeout = 5000` a
contended write parks its thread for up to five seconds of zero CPU. Nothing bounds how many requests
may be inside SQLite at once.

The likely shape of the fix is a bound on database-path concurrency rather than an attempt to make
SQLite asynchronous. Deliberately not designed further here — the dump decides whether this is even
the right target, and designing it now would be exactly the speculative work this investigation keeps
paying for.

Recorded for the record: the read path is **exonerated** at 3,688 successful reads/second and p99
57 ms at 500 concurrency (`api_user_500`). The write path was not exercised at that concurrency in
this run and remains untested.

### 5.2 Unconditional — round-end outbox

`src/Basil.Application/Backgrounds/MatchRoundEndOutbox.cs`. Not a cause of the 10:56 collapse — the
outbox-full burst is at 10:39, seventeen minutes and four healthy scenarios earlier — but a real
defect:

* `ExecuteAsync` (lines 85-89) drains strictly serially: one write at a time, each opening its own
  connection. Whatever slowed round-end writes at 10:39 would fill a 128-slot queue at that drain
  rate.
* `DrainAsync` (lines 78-82) polls a 10 ms `Task.Delay` with no timeout and never returns while the
  consumer is stalled. Its only caller is `MatchMembershipService.cs:879`.

Needs its own investigation of *why* round-end writes became slow, which the missing log window
(Phase 1 fixes that) should reveal on the next run.

## Testing

Per CLAUDE.md rule 8 and [`testing.md`](../docs/for-developers/testing.md), Serilog message text is
explicitly **not** a pinned contract, so this work is deliberately not covered by log-assertion
tests. No test in `tests/` references `ApiRequestLoggingMiddleware`, `RequestIdLoggingMiddleware`,
`CategoryEnricher` or `UseSerilogRequestLogging`, so nothing breaks by construction.

What is verified, and how:

| Change | Verification |
|---|---|
| Phase 1 sink limits | Load run produces rolled, untruncated files |
| Phase 3.1 async sinks | Phase 2's dump shape does not recur; no thread parked in a sink |
| Phase 3.2 request levels | Re-run log contains zero `-> 2xx` request lines at default level |
| Phase 3.5 header allocation | `Geolocation.PhraseIpAddress` behaviour unchanged — covered by existing login tests; confirm which ones before editing |
| Everything | `dotnet test` (1597 passing), `dotnet build -c Release` clean |

The one place a new test is warranted is Phase 3.5, if the existing suite does not already pin
`PhraseIpAddress`'s header-precedence behaviour (`CF-Connecting-IP` → `X-Forwarded-For` first entry →
`X-Real-IP`). Check before changing it; add a regression test if that precedence is unpinned.

## Open decisions for the user

1. **Phase 2 before Phase 3, or not?** The plan says yes, and explains the cost of the alternative.
   Skipping it means RC11's mechanism is never established.
2. **`fileSizeLimitBytes` value.** 256 MB proposed. Larger means fewer files, more lost on a
   truncation bug; smaller means more rolling churn.
3. **Async sink overflow: drop silently, or add a monitor?** Drop proposed, on simplicity grounds.
4. **Keep the console sink at all in a published deployment?** It is needed for Docker stdout
   collection. Keeping it, async-wrapped, is the proposal.
5. **Accept the header case-sensitivity fix in Phase 3.5?** Reading the three IP headers through
   `request.Headers` makes lowercase `x-forwarded-for` work where today it is silently ignored. It is
   a correctness improvement on a login path, so it needs a yes rather than being absorbed into a
   performance change.
